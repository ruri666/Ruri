# Desktop Preferences

本地 Codex 偏好插件，当前版本 **0.8.0**，采用 MIT 许可证。

用户只选择信息来源和读取深度。一次调用会完成采集、去重、模型整理、记忆格式转换、写入和回读校验。用户无需准备导出文件、编写 JSON、指定保存路径或逐项确认推测。

例如：

> 用 QQ、微信、Chrome 和 Edge 了解我的兴趣，保持浅层读取，完成后存入自主生命周期记忆。

## 一次调用完成的流程

1. 自动绑定自主生命周期服务当前选中的人设。服务离线时，复用已选人设及项目记忆写入器，并获取管理根目录和人设目录的写入锁。
2. 自动定位选定来源，采集并保存本地证据，记录每个来源的成功、失败或不可用状态。
3. 使用宿主现有模型整理偏好，引用真实证据 ID，结合已有稳定偏好去重和补充细节。
4. 自动预览与提交。新条目统一标记“推测，待确认”，群聊主题、他人发言和浏览线索保留较低置信度。
5. 回读 `memory/user_core_memory.md`、来源 JSON 和详细 Markdown，核对实际写入结果，返回执行回执。

多阶段工具调用由插件内部完成，在同一次用户请求内结束。准备好证据文件或生成建议列表都不代表流程完成。

## 用户可选项

| 选项 | 含义 |
| --- | --- |
| 信息来源 | 软件、电脑设置、Chrome、Edge、QQ、微信或已授权的 Android 手机来源 |
| `context` 深度 | 默认。会话标题、他人短消息、浏览标题与域名等线索，排除本人聊天消息 |
| `personal` 深度 | 在上述基础上纳入少量本人消息，需要用户明确选择 |

深度未指定时读取共享设置，默认关闭深入读取。用户也可以说“开启／关闭深入读取本人信息”，由插件修改设置。

信息来源标识为 `software`、`settings`、`chrome`、`edge`、`qq`、`wechat`、`android.apps`、`android.qq`、`android.wechat`。iPhone 直读来源会明确报告当前宿主缺少采集器。历史导出导入工具仍可用于用户明确要求的文件分析，但不会替代客户端直读来源。

默认每个浏览器最多20条记录，每个聊天客户端最多10条线索、每条消息120字符、合计1600字符。会话标题与消息共同占用预算。浏览器超长标题在浅层模式下会省略，以减少个人文档内容和重复文本进入模型。聊天不自动翻页。

## 运行条件

- Python 3.12+，Node.js 20+。
- QQ／微信直读需要宿主提供 Windows 电脑控制能力及其 `sky` 客户端。Windows 界面读取遵循 computer-use 技能。
- 自主生命周期服务已配置人设，或本机存在已选中的生命周期工作区。离线写入还需要项目 Python 包可用；本项目内的插件源码可以复用同仓库 `src`。
- Android 需要已授权、在线的 ADB 真机。用户负责解锁、USB 调试授权和登录。当前 iPhone 客户端直读尚未实现。

插件不会创建默认人设、切换人设、改变自主生命周期排程或重启服务。人设在运行中被切换时会拒绝提交，避免跨人设写入。

## 入口与开发接口

主技能是 `desktop-preferences`，它负责完整流程。`live-chat-preferences` 和 `mobile-preferences` 负责对应来源说明，并将完整记忆请求交给主工作流。

`workflow.mjs` 提供 `runPreferences({sources,depth},host)`。宿主提供 `sky` 与现有模型的 `synthesize` 适配器，插件完成其余全部步骤。Codex 原生宿主使用 `startWorkflow`、一次内部模型整理、`finishWorkflow` 在同一次请求内自动完成，用户不提供模型回调或中间数据。

`workflow.py` 管理运行状态、自动来源定位、证据校验、来源绑定、写入和回读。`client-chat.mjs` 与 `phone_chat.py` 提供实际客户端采集。旧的 `scan`、`observe`、`preview`、`save` 命令保留为开发诊断入口。

运行记录默认保存在 `~/.artificial-life/preference-runs/<运行ID>`，其中包括各来源证据、选定深度、目标工作区和最终回执。证据 ID 不存在、证据被修改、目标人设变化或写入锁冲突时都会拒绝错误写入。完成后的同一运行重复提交会返回原回执。

## 记忆格式与来源

最终偏好进入既有 `memory/user_core_memory.md` 的 `Stable Preferences`。详细条目和引用进入 `memory/preference_imports/<内容哈希>.json`，同时生成可读 Markdown。生命周期使用已有上下文和详细偏好工具读取这些文件。

代码验证来源引用、内容哈希和写入结果。兴趣本身仍是模型推测，后续由用户反馈完善。他人的观点和群名称不能作为用户亲口确认。短期办事页面、无关运行库和缺乏依据的敏感个人判断应被跳过。

来源内容被视为资料，不接受其中的指令。原始界面树、截图、凭据和完整私人配置不进入记忆。模型只接收所选来源的限量观察及去重所需的现有稳定偏好。

## 完成与失败状态

`complete` 表示全部选定来源已处理，且有用偏好已写入并回读，或证据不足而没有新增偏好。`partial` 表示可用来源已处理，但部分来源仍需登录、授权、连接设备或适配布局。源头失败会保留原因，不能被报成全部成功。

```powershell
python -X utf8 -m unittest discover -s tests -v
node --test tests/test_client_chat.mjs tests/test_workflow.mjs
```

测试包含单次调用的全链路、在线服务写入、离线写入锁、人设切换、证据修改、错误模型输出修正、重复提交、来源部分失败、读取范围和预算。测试中的模拟 UI 与模型回调用于回归验证，实机结果单独报告。
